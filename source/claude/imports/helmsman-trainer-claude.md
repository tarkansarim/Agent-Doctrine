# Captioning Tool — Project Rules

## ⛔ No Fire-and-Forget for Runtime-Critical Behaviors (MANDATORY)

Certain behaviors are RUNTIME-MANDATORY — automatic for EVERY applicable run, wired
**permanently in code** (never a one-off API call or CLI flag an agent must remember), working
across ALL training kinds and architectures (text-to-image AND image-edit AND every model), and
**verified on the Mission Control screen before the work is called done**. NEVER "fire and forget":
never launch a long or important operation and assume a runtime contract held — confirm it fired.
If you find one of these gated to a single path (e.g. `is_edit`-only), that is a bug — generalize it.

Non-negotiable runtime contracts:
- **Pre-training baseline samples.** Before the first training step, render the step-0 baseline
  (base model, trained LoRA bypassed) with the run's sample prompts and stream it into Mission
  Control as the untrained "before" reference. Applies to ALL training kinds, not just `image_edit`.
  A run that begins training without a streamed step-0 baseline is broken.
- **Activity Log wiring of EVERY output-producing process.** Every background process that produces
  output (the diffusion-pipe train/caching log, the ComfyUI sampler log, any spawned worker) must be
  registered as a Mission Control activity-log source permanently in code — like ComfyUI and the
  live watch already are — so output is visible from the start, including long pre-folder phases such
  as latent caching. An empty Activity Log during a running operation is a bug.
- **Live observability of long operations.** Never drift headless: the live watch (step/loss/samples)
  must auto-register when a run starts and re-register across every resume.
- **Fresh run auto-clears stale training data.** Starting a NEW (non-resume / non-extend) training
  must automatically clear Mission Control's training lineage / scalar (loss) chart / watch so old
  and new runs never mix in the graph — wired into the launch path, NOT a manual "Clear Training"
  the agent must remember. It clears MC's own index only, never the trainer's output folders.

When you add or touch any such behavior, make it automatic + permanent + cross-kind + verified. If
you cannot verify it fired on screen, do not claim the operation is healthy.

In that mode, Mission Control reuses the regularization role as the Control lane, keeps buckets as target-image balance buckets, and Export Handoff writes paired `target/` and `control/` folders instead of `img/` and `reg/`. The export must require a trigger word, enforce one selected control image with the same basename for each selected target image, write trigger-only adjacent `.txt` captions **for the target images only** (Control-lane images get NO `.txt` — `_export_entry(write_caption=False)`), and record `trainingKind=image_edit` plus `imageEditPairs` in the manifest. So `control/` must be image-only (covered by the image-edit export test asserting no `control/*.txt`). Edit-2511 is selected by `diffusers_path` (the `qwen_image_edit_2511` preset → `Qwen-Image-Edit-2511` snapshot) plus `control_path`, so `type = qwen_image` in the Training Parameters is the shared model class, not the base model. `diffusers_path` must be the diffusers *snapshot* root (directly containing `transformer/`, `vae/`, `text_encoder/`), NOT the HF hub *wrapper* dir `…/hub/models--Qwen--Qwen-Image-Edit-2511/` (children `blobs/ snapshots/ refs/`), because the loader reads `Path(diffusers_path)/'transformer'`; the wrapper crashes the launch. `prepare` handles this automatically — `_normalize_diffusers_root` detects the HF wrapper signature (`blobs/`+`snapshots/`) and descends to the `refs/main` commit (newest-snapshot fallback) for any HF-cached diffusers model, RUNTIME, with no hand-pasted snapshot hashes. To EXTEND a finished run to a higher `--max-steps` (e.g. 3400→6800), pass `--existing-run-root` + the higher `--max-steps` AND re-pass every tuned override (`--save-every-n-steps`/`--checkpoint-every-n-epochs`/`--num-gpus`/`--micro-batch-size`/`--gradient-accumulation-steps`/`--resolutions`): prepare runs UNCONDITIONALLY and rewrites the config-dir `train.toml` from the manifest, so omitting `--max-steps` exits immediately at the old max (and flips the watch COMPLETED) and any un-re-passed override is clobbered to the manifest's untuned default (breaking the cadence/resume grid); the run-folder `train.toml`/`latest` are inert/auto-repointed. Pass `--sample-every-checkpoint` (instead of `--sample-points`) to sample at EVERY checkpoint: the runner derives the sample points as multiples of `--save-every-n-steps` up to `--max-steps`, so every realized graph node gets a sample and there is no hand-aligning of sample points to the checkpoint grid (this is the user's default preference — every checkpoint has samples). `checkpoint_pair_ready`/`resolve_resume_checkpoint_dir` fold a nearby-preceding `global_step` (within 16 steps) when no at-or-after resume tag exists, so step-vs-epoch checkpoint misalignment (e.g. step330 + global_step328) never stalls the loop; lineage synthesizes a step-0 baseline node, and the graph shows only the baseline, sample-bearing checkpoints, and the single latest resume-only checkpoint (intermediate bare `global_step`s stay in the table only). Runtime vs agentic split: per-checkpoint+baseline sampling, stop/sample/resume sequencing, node detection, AVIF→PNG staging, the static seed, output selection, checkpoint pairing, and baseline synthesis are runtime; control images, edit prompt, workflow file, sample points, checkpoint schedule, trigger word, and launch timing are agentic decisions documented for the driver. Never fire-and-forget — supervise the managed run. Qwen-Image-Edit training config (measured on 96GB Blackwell): `transformer_dtype='float8'` and `activation_checkpointing=true` are REQUIRED (bf16 weights ~40GB OOM; no-checkpointing needs ~91GB activations and OOMs even at float8 — the control image is concatenated, ~2x sequence; float8 has no native FP8 GEMM so it is a memory necessity, not a speed win). Resolution 512 is the clean per-step win over native 640. Bigger batch gives no throughput gain once GPU-saturated (~1.5 s/sample), so mirror ai-toolkit with micro_batch=1 + gradient_accumulation=1 (effective batch = num_gpus). There is no ~9x gap vs ai-toolkit — that was an s/it↔it/s unit flip (ai-toolkit ~2.46 s/it/1 GPU vs diffusion-pipe ~1.5 s/sample); long wall-clock comes from over-sized training budgets (a per-run manifest's `ga=4`×3300 steps = 4x ai-toolkit's ~6600 presentations; the code default is `ga=1`). MANDATORY before launching with ≥2 GPUs (or any `global_batch = micro_batch × gradient_accumulation × num_gpus ≥ 2`): warn the user that diffusion-pipe batches per aspect-ratio bucket and DROPS leftover partial batches (integer division, `utils/dataset.py:383`), so any AR bucket whose image count isn't divisible by `global_batch` loses images every epoch and the steps/epoch stops being a clean multiple of the dataset size (breaking ×N cadences). Example: 34 imgs (AR buckets 16/17/1) at global_batch 2 → 16 steps/epoch, only 32 images used, 2 dropped/epoch, cadence lands on 320 not 340; on 1 GPU all 34 are used and 340 = 10 epochs.
