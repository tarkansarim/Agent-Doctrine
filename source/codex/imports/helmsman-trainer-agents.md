## ⛔ RULE 0 — KEEP THE AGENT-FACING DOCS IN SYNC (READ FIRST, NON-NEGOTIABLE)

**This is a hard definition-of-done for public agent-driveable surface changes — not advice. Do not expand tiny reuse-only fixes into doctrine churn.**

A change to a tool-visible surface — adding, renaming, removing, or changing the public semantics of a Mission Control control, REST/WebSocket endpoint, Qt GUI bridge control, embedded command, event, recipe/recipe-kind, classifier/bucketing behavior, export/training contract, or other agent-driven capability — is **NOT complete and MUST NOT be committed or called "done"** until it is reflected, **in the same change**, in the required owning surfaces below.

Tiny/direct fixes that only reuse an already documented endpoint/control/skill contract are exempt from AGENTS/CLAUDE/skill edits. Examples: duplicating an existing menu action while sending one different already-supported flag, fixing a typo, preserving a seed through an existing regenerate path, or changing a label without changing the agent contract. For those, keep the patch to code and exact user-visible verification; do not touch `AGENTS.md`, `CLAUDE.md`, or skills unless the reusable agent-facing contract changed.

For non-exempt public surface changes, update:

1. **The tool surface** — server endpoint + Qt bridge control + embedded command + event (so automation can still drive it).
2. **The owning `skills/<skill>/SKILL.md`** — the operating source of truth an agent loads. A capability not in its skill is undiscoverable, therefore broken.
3. **`CLAUDE.md`**.
4. **`AGENTS.md`** (this file).

Hard requirements:
- First classify whether the request is tiny/direct reuse or a public contract change. If it is tiny/direct reuse, state the exemption and keep the scope narrow.
- For public contract changes, do the docs **as part of the same change**, not "after I verify" / "later" / "once it works." Building + testing a feature and leaving the docs trailing is a violation, even if the code is correct.
- Before claiming a tool-visible change is done, **grep the skill + CLAUDE.md + AGENTS.md for the new control/endpoint/command/event/function name** and confirm it appears. If it doesn't, you are not done.
- Add a **new** skill only when the change is a new *category* of work; otherwise extend the existing one.

## ⛔ NO FIRE-AND-FORGET FOR RUNTIME-CRITICAL BEHAVIORS (NON-NEGOTIABLE)

Some behaviors are RUNTIME-MANDATORY — automatic for EVERY applicable run, wired **permanently in
code** (never a one-off API call or CLI flag an agent must remember), working across ALL training
kinds and architectures (text-to-image AND image-edit AND every model), and **verified on the

- **Pre-training baseline samples** — before the first training step, render the step-0 baseline
  (base model, trained LoRA bypassed) with the run's sample prompts and stream it into Mission
  Control. ALL training kinds, not just `image_edit`. Training that starts with no streamed step-0
  baseline is broken.

  the ComfyUI sampler log, and any spawned worker must be registered as MC activity-log sources
  permanently in code (like ComfyUI + the live watch), visible from the start including latent
  caching. An empty Activity Log during a running operation is a bug.
- **Live observability** — never drift headless; the live watch auto-registers on start and
  re-registers across every resume.
- **Fresh run auto-clears stale training data** — a NEW (non-resume/non-extend) training must

  trainer output folders.

If you cannot verify a runtime contract fired on screen, do not claim the operation is healthy.

Parameter edits must write through to the imported/watched run's backing TOML or JSON config, preserve the existing value type, refresh the stored lineage `trainingParameters`, and reject read-only run metadata rows such as `run.config_path`; agents should use the server or Qt bridge route instead of patching trainer config files directly.

Regularization in diffusion-pipe IS supported — via a second dataset `[[directory]]` (data mixing), NOT a prior-preservation loss. NEVER conclude "diffusion-pipe can't do regularization." diffusion-pipe has no kohya/DreamBooth machinery (`with_prior_preservation`, `class_data_dir`, `prior_loss_weight`, `class_prompt`) and no per-directory `is_reg` flag; do not grep for those, fail to find them, and wrongly declare regularization unsupported (that exact mistake happened once and must not recur — read the user's OWN past runs' `dataset.toml` before answering). Regularization here means adding the reg images as an extra plain `[[directory]]` of image+`.txt` pairs weighted by `num_repeats`: they are ordinary training samples mixed into the batch, and that mixing is what balances the model (e.g. pulling shading back from a training set whose uniform lighting drags all shading toward it). Helmsman already wires it — Export Handoff writes `img/`+`reg/`, `POST /training/diffusion_pipe/prepare` auto-detects `reg/` in the export root and emits the second `[[directory]]`, and the manifest records `regularizationImageDir`/`regularizationMode` (proven reference run: `helmsman_exports/small_con_male_fork_step5760_20260527/`, an `img/`+`reg/` pair). Reg images MUST be captioned (diffusion-pipe `skip_empty_caption` defaults True, so blank-caption reg images are silently dropped), in the SAME detailed natural-language style as the training captions but WITHOUT any trigger word — class-only/minimal captions are the kohya prior-preservation convention and are wrong for diffusion-pipe because the model learns caption→image for each reg image. Proven reg caption style: one flowing sentence — framing → subject → clothing/action → setting → explicit lighting → composition. `num_repeats` controls the reg fraction/strength (aim ~20–50% for modern Flux/z-image/Qwen models, which forget faster than SD) and is settable on `POST /training/diffusion_pipe/prepare` via `regularizationNumRepeats`/`imgNumRepeats` (default 1, floored at 1, recorded in the manifest; previously hardcoded to 1), so reg weight is tunable without regenerating; the reg directory need not pair 1:1 with training. MODERN reg-captioning rule (Flux/Flux.2/z-image/Qwen-Image, not SD1.5/SDXL): caption reg images as the BASE model would itself generate — accurate natural language, never class-only/blank; z-image/Qwen prefer accurate-but-tight captions with no "the style of the image is…" meta-commentary; for a lighting-balance goal the reg captions MUST name their varied lighting. Modern loss-based reg mechanisms — ai-toolkit `is_reg`+Differential Output Preservation and SimpleTuner `is_regularisation_data` — are absent from diffusion-pipe (it regularizes only by 2nd-directory data-mixing), as is kohya-style prior-preservation *loss* (class prompt + `prior_loss_weight`); for those, use ai-toolkit/SimpleTuner/kohya. Full modern reg-captioning guidelines live in the `regularization-generation` skill; the `diffusion-pipe-training` skill carries the full "Regularization" section.

Image-edit training is recipe-specific. `Recipe.trainingKind` is `text_to_image` by default; when it is `image_edit`, Mission Control treats the regularization role as the Control lane for target/control pairing, while buckets still describe target image balance. Control-lane images are never VLM-bucketed; they are paired to their target by file basename (`image_edit_control_bucket_pairings`) and mechanically inherit that target's bucket plus `regularizationProvenance.sourceImageId` (`_apply_image_edit_control_pairings`, `bucketSource=regularization_pair`), so each control mirrors its target's bucket, the Caption View pair inspector shows it next to its target, and it does not sit in the Image Pool. This pairing is RUNTIME/automatic (never a manual babysit step): it runs after a scan reconcile, after a target classification pass, after a manual target re-bucket (`POST /images/{id}/bucket` on a training image), and on `Repair Control` (`POST /regularization/classify`). The Caption View uses "control" (not "regularization") terminology for `image_edit` recipes. Export Handoff must require a trigger word, copy selected target images into `target/`, copy selected control images into `control/`, enforce exactly one selected control image with the same basename for every selected target image, and write trigger-only adjacent `.txt` captions **for target images only** — Control-lane images get NO `.txt` (`_export_entry(write_caption=False)`). Control captions are forbidden because diffusion-pipe's `control_path` loader globs the control dir with `glob('*')` and keys by file STEM (`utils/dataset.py:633`), so a `4.txt` beside `4.png` collides on stem `4`, can shadow the PNG, and makes diffusion-pipe load the text file as a control image and crash; `control/` must be image-only (asserted by the image-edit export test). Image-edit datasets use ONE shared trigger/prompt as the caption for EVERY target/control pair — the edit instruction itself (e.g. `Convert shading to photoreal`), identical across all images — NOT detailed or varied per-image captions, because established Qwen-Image-Edit LoRA guidance is to train with just the trigger word (detailed/varied captions reduce edit-model accuracy). The single edit instruction doubles as the trigger word and the prompt, so the export's trigger IS each target's caption. `POST /training/diffusion_pipe/prepare` accepts `trainingKind=image_edit` and writes a diffusion-pipe dataset `[[directory]]` with `path = target/` and `control_path = control/`; text-to-image exports keep the existing `img/` plus optional `reg/` behavior. The diffusion-pipe model `type` for image-edit is `qwen_image` and that is correct — there is no separate `qwen_image_edit` type (`models/qwen_image.py` implements both; Edit mode is automatic when control images are present, concatenating `control_latents` with the noisy latents). Edit-2511 is selected by `diffusers_path` (the `qwen_image_edit_2511` preset) + `control_path`, so `type = qwen_image` in Training Parameters is the shared class, not the base model. `diffusers_path` must be the diffusers *snapshot* root (directly containing `transformer/`, `vae/`, `text_encoder/`), NOT the HF hub *wrapper* dir `…/hub/models--Qwen--Qwen-Image-Edit-2511/` (children `blobs/ snapshots/ refs/`), because the loader reads `Path(diffusers_path)/'transformer'`; the wrapper crashes the launch. `prepare` resolves this automatically — `_normalize_diffusers_root` detects the HF wrapper signature (`blobs/`+`snapshots/`) and descends to the `refs/main` commit (newest-snapshot fallback) for any HF-cached diffusers model, RUNTIME, no hand-pasted snapshot hashes (covered by `NormalizeDiffusersRootTests`). Default checkpoint cadence for the 34-image mecha set is 10 epochs (→ 340-step checkpoints: 340/680/1020 for 1020 steps), NOT 5 epochs/170. diffusion-pipe renders no checkpoint samples for image-edit runs; `scripts/mission_control_diffusion_pipe_smoke.py --training-kind image_edit --edit-control-images <paths> --edit-prompt "<instruction>" --workflow <qwen-edit-sample-workflow>` drives them by patching the workflow's enabled `LoadImage`/`Positive` `TextEncodeQwenImageEditPlus`/non-Lightning `LoraLoaderModelOnly`/Seed/`SaveImage` nodes (detected by type/title/mode via `detect_edit_workflow_nodes`, overridable), keeping the Lightning LoRA and ControlNet, using one static `--edit-seed` for all samples, re-encoding AVIF/non-PNG controls to PNG, and selecting the `SaveImage` `type=output` history result. Samples write to `<run>/samples/step_<step>/` for the watcher. Without `--existing-run-root` the runner drives a full managed loop: it prepares the diffusion-pipe config from the manifest (forwarding `trainingKind=image_edit` so prepare writes `target/`+`control/`+`control_path`), optionally renders a `--sample-baseline` step-0 baseline BEFORE training starts (base model with the trained-adapter node bypassed; staged then promoted into the run's `samples/step_000000/`, so the GPU is free for training), then trains→stops→samples→resumes at each `--sample-points` step (or, with `--sample-every-checkpoint`, at every checkpoint — sample points are derived as multiples of `--save-every-n-steps` up to `--max-steps`, the user's default so every realized graph node has samples and there is no hand-aligning of sample points to the checkpoint grid). To EXTEND a finished run to a higher `--max-steps` (e.g. 3400→6800), pass `--existing-run-root` + the higher `--max-steps` AND re-pass EVERY tuned override (`--save-every-n-steps`/`--checkpoint-every-n-epochs`/`--num-gpus`/`--micro-batch-size`/`--gradient-accumulation-steps`/`--resolutions`): prepare runs unconditionally and rewrites the config-dir `train.toml` from the manifest, so omitting `--max-steps` exits immediately at the old max (and flips the watch COMPLETED) and any un-re-passed override reverts to the manifest's untuned default and breaks the cadence/resume grid; for image-edit use an explicit new-only `--sample-points` (not `--sample-every-checkpoint`, which re-renders old samples) and drop `--sample-baseline`; re-index with `POST /training/lineage/import_diffusion_pipe_run` afterward if the watch completed before the final samples landed. `checkpoint_pair_ready`/`resolve_resume_checkpoint_dir` fold a nearby-preceding `global_step` (within 16 steps) when no at-or-after resume tag exists so epoch-vs-step schedule misalignment does not stall the loop, and lineage synthesizes a step-0 baseline node. The Training Lineage graph shows only the baseline, sample-bearing checkpoints, and the single latest resume-only checkpoint; intermediate bare resume `global_step`s stay in the table but are hidden from the graph. The runtime/agentic boundary: per-checkpoint+baseline sampling, stop/sample/resume sequencing, node detection, AVIF→PNG staging, the static seed, output selection, checkpoint pairing, and baseline synthesis are runtime; control images, edit prompt, workflow file, sample points, checkpoint schedule, trigger word, and launch timing are agentic decisions documented for the driver. Never fire-and-forget — supervise the managed run. Measured Qwen-Image-Edit config (96GB Blackwell): `transformer_dtype='float8'` + `activation_checkpointing=true` are required (bf16 OOMs on ~40GB weights; no-checkpointing OOMs on ~91GB activations because the control image is concatenated, ~2x sequence; float8 is a memory necessity with no native FP8 GEMM speedup). Resolution 512 is the per-step win over 640; bigger batch gives no throughput gain once GPU-saturated (~1.5 s/sample), so mirror ai-toolkit with micro_batch=1+gradient_accumulation=1 (effective batch = num_gpus). No ~9x gap vs ai-toolkit (s/it↔it/s unit flip); long wall-clock is over-sized training budgets, not slow compute. MANDATORY before a ≥2-GPU launch (global_batch = mb×ga×gpus ≥ 2): warn the user that diffusion-pipe drops leftover partial batches per AR bucket (integer division, utils/dataset.py:383), so images whose AR-bucket count isn't divisible by global_batch are dropped every epoch and steps/epoch stops being a clean multiple of the dataset size (34 imgs at global_batch 2 → 16 steps/epoch, 32 used, 2 dropped, cadence 320 not 340; 1 GPU uses all 34, 340 = 10 epochs). Offer: add images for divisible buckets, accept drops + non-aligned cadence, or use 1 GPU. AR-bucketing does NOT crop (resizes preserving aspect); cropping only if enable_ar_bucket is off. Keep checkpoint cadence epoch-aligned so adapter step* and resume global_step* coincide, but do NOT assume steps/epoch = ceil(images/(mb×ga×gpus)) — `enable_ar_bucket` lowers it; verify from the first `global_stepN` (steps/epoch = N / checkpoint_every_n_epochs) and set save_every_n_steps to that same global_step cadence, sampling only on its multiples. Misaligned step340 vs global_step320 ⇒ checkpoint_pair_ready False everywhere ⇒ managed loop stalls; relaunch with the corrected save cadence. Smoke runner overrides: `--resolutions`, `--gradient-accumulation-steps`, `--micro-batch-size`, `--save-every-n-steps`, `--sample-every-checkpoint` (derive sample points = `--save-every-n-steps`×N up to `--max-steps`; overrides `--sample-points`), `--max-steps`, `--checkpoint-every-n-epochs`, `--num-gpus`. Observability is mandatory (never drift into headless training): the runner auto-registers the Mission Control live-watch via `--mission-control-url` (default `http://127.0.0.1:8200`, empty disables) when the run folder appears and re-registers on resume; the live step/loss panel updates immediately while a lineage node only appears at the first checkpoint and samples at the first sample point.
