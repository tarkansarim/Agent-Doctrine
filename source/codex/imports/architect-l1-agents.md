# Architect-L1 Supervisor Rules

This file is for the supervisor/building agent operating this project. Keep
these rules out of L1/L2 isolated ancestry unless a replay explicitly earns a
smaller lower-level primitive. L1 and L2 react to local pressure, not to this
theory.

## Core Law

Seed the substrate for contact, pressure, memory, replay, and promotion. Leave
the high-level solution unseeded.

Before adding a mechanism, gate, queue, memory surface, agent role, review lane,
or runtime automation, ask whether the behavior can emerge from lower-level
pressure, occlusion, affordance, trace, replay, structural dependency, or
containment boundaries.

Promote the condition that made useful motion repeat, not the visible behavior
itself.

## Harness Rebuild Entry Sequence

For Emergence Build Harness or any Harness Architect rebuild, start from the
actual first execution path, not from the mature feature list.

The boot loop is:

```text
user prompt arrives
-> prompt is preserved as contact
-> next needed phenomenon is derived from that prompt
-> ancestry gap/support is classified
-> smallest next build step is created from existing tissue
-> continuation tries to use it
```

Treat EBH architecture as local growth rules, not a fixed blueprint. Keep the
main trunk sequential while one earned path can carry the next motion. Branch
only when local pressure exposes an independent support surface, a hardening
sidecar can move without mutating the mainline, or an existing tissue branch may
carry part of a bolted-on need. Join branches only when the combination reduces
friction, preserves continuation, or exposes contradiction that neither branch
can expose alone. Prune or demote branches that do not carry flow, duplicate
existing tissue, hide contradiction, or only make the graph look organic.

Do not begin by recreating target lanes, control registries, launch manifests,
or other mature Harness Architect features. Those are later support surfaces
unless the prompt-to-next-phenomenon loop makes them locally necessary.

When no ancestry exists yet, add the smallest ancestral support needed to
bootstrap the next step, label it as support or first-contact candidate, and
keep replacing bolt-on ancestry with locally earned tissue as soon as the loop
can continue from its own artifacts.

When reporting on a harness rebuild, always separate two classifications:

- what is bolted-on ancestral or hardening support.
- what emerged from prior locally discovered phenomena.

Do not let a local checker passing blur origin. A phenomenon can have local
first-contact evidence while still having a bolted-on origin. Tissue claims
require locally earned continuation under pressure, not just a checked artifact.

Include a concise `Current EBH Capability Chain` section that lists what EBH can
already do, in order, and the main thing it still cannot do yet. This is a user
comprehension surface, not a promotion claim.

Also include a concise `Self-Improvement / Rule Updates` section. It must say
whether self-improvement was needed, whether the working approach changed,
whether repo `AGENTS.md` changed, and whether any repo-owned skill source
changed. Use `none` when nothing changed.

These two sections are a closing report. Always emit them when you genuinely
yield control to the user — when you stop for a real blocker, required user
decision, safety concern, or external limit (per Autonomous Work Rhythm), or
when the user asks you to stop. They are also welcome in any intermediate status
message you choose to send while continuing. What they must never do is cause a
stop: completing a work round, status, replay, gate close, verification, or
commit is not a yield point. If the user has told you to keep going until they
say stop, keep working through those boundaries and carry the report forward to
the genuine handoff — producing the report is not the end of your turn.

EBH must apply the same discipline to products it builds. A product request may
seed bolted-on product boundaries because no product tissue exists yet, but
those boundaries are not earned features. Treat them as pressure surfaces. New
features must be derived from the gradients between existing local tissue,
contact evidence, and those boundary pressures. As more tissue connects, revisit
the bolted-on boundaries: split them, demote them, or replace them with the
lower phenomena the tissue reveals.

Phenomenon legitimacy is layered. A candidate is stronger only when it has
signals in all three directions:

- lower-level composition: it is made from lower phenomena that local pressure
  actually discovered.
- lateral functional fit: it works hand in hand with surrounding phenomena,
  exchanges pressure or support, transfers stress without hiding it, and exposes
  contradiction when removed.
- higher-level service: it becomes a usable element for a higher phenomenon
  that can continue from it without hidden supervisor meaning.

Do not promote from graph connection alone. Missing lower parents, weak lateral
fit, or no higher continuation are pressure to reprobe, split, or demote the
candidate rather than call it tissue.

Use `layer` narrowly. A true phenomenon layer means composition: a phenomenon is
one layer higher only when multiple lower live phenomena combine into it. A
one-parent continuation extends sequence depth, not composition height. Reports
and pyramids must keep `composition band` separate from `sequence depth` so a
long spine is not mistaken for mature layered tissue.

Each phenomenon record must also say what the phenomenon is for. Treat those
purpose/use-case descriptions as the current map of available tissue instead of
maintaining a separate duplicate map unless the descriptions stop being enough.
When a new feature must be bolted on, immediately scan the existing phenomenon
descriptions for anything that can already accommodate part of it alone or in a
sideways join. Replace or shrink the bolt-on as soon as existing tissue can
carry the work.

## Autonomous Work Rhythm

When the next move is clear and no human choice is needed, keep working through
the work instead of breaking it into small increments. Give a short heads-up
before long-running work, then batch routine progress updates while continuing.
A phase, verification run, commit, cleanup pass, or quick scan with no immediate
gap is not a handoff point. If no immediate gap appears, expand the scan or move
to the next useful surface. Hand control back only for a real blocker, required
user decision, safety concern, or external limit that prevents more useful
progress in the current turn.
Never stop merely because a natural boundary, safe boundary, commit boundary,
verification boundary, or integration boundary was reached.
Emitting the `Current EBH Capability Chain` or `Self-Improvement / Rule Updates`
report is itself not a handoff. A closed replay, a passing gate, or a written
report section is exactly the kind of boundary you must not stop at. When the
user has asked you to continue until they say stop, only an actual blocker,
required decision, safety concern, external limit, or an explicit stop request
ends the turn — never the act of reporting.

## Parallel/Subagent Work

Use subagents or parallel worker lanes whenever the work can be split without
weakening evidence, losing local contact, or creating hidden supervisor meaning.
Prefer parallel lanes for independent audits, source mapping, pressure/hardening
sidecars, route variation, broad searches, and separate verifier/test repair
hypotheses. Keep the mainline responsible for integration and final evidence:
worker output is input to verify, not authority to trust.

Do not parallelize steps that depend on the same immediate artifact mutation,
the same unresolved tool failure, or a sequence where the next gate must emerge
from the previous contact. In those cases, keep the trunk sequential and split
only adjacent review, hardening, or mapping work.

## Claim Filter

Classify every idea, defect, replay result, or proposed primitive before it
drives implementation:

- `proved`: local pressure, raw contact, and replay survived.
- `hypothesis`: imported, inferred, or plausible but not locally confirmed.
- `fantasy`: coherent idea with no pressure path, contact signal, or replay
  route.
- `danger`: depends on hidden motive, managed feedback, arbitrary gate shifts,
  false closure, or non-rejectable pressure.

`Proved` items can become local tissue or promotion evidence. Hypotheses may
shape probes. Fantasy stays as notes. Danger is redesigned or set aside.

## Pressure Design

When a desired behavior is missing, replace "how do I add it?" with:

- what absence would make the behavior necessary?
- which direct shortcut is best occluded?
- what raw contact would reject the hypothesis?
- what affordance makes the useful motion the lowest-friction path?
- what replay variation would prove this is not a one-off?

Use progressive occlusion for important, brittle, ambiguous, or overtrusted
goals: occlude the trusted lane, discover another lane, verify it independently,
compare successful lanes, and extract the invariant.

Environment-created boundaries are the default shape: add the smallest surface
that the last replay proved missing. A file, socket, hook, wrapper, or queue is
earned only when it answers local friction and leaves the high-level behavior
unseeded.

## Complexity Rule

Complexity comes from gates opening adjacent gates, not from top-down design.

```text
primitive pressure
-> allowed move
-> gate opens
-> new affordance appears
-> next pressure becomes visible
-> neighboring tissue connects
```

After a boundary closes, record what gate opened, what new boundary became
visible, what prior tissue enabled it, and what next pressure has traction.

## Elasticity First

Prefer structures that absorb ordinary mistakes through trace, slack,
compensation, replay, and nearby tissue. Strong wording and tight control belong
at containment boundaries, not throughout the whole process.

Minor mistakes are useful deformation when they stay visible, bounded, and
recoverable. The encoding preserves enough slack for the system to keep moving,
learn what bent, and retune the lower-level pressure later.

## Tissue, Slack, And Compensation

Build robustness from interconnected tissue, not isolated rescue patches.
When several behaviors grow from the same lower-level affordance, stress can
travel through the shared substrate and neighboring tissue can compensate.

Keep this distinction clear:

- containment boundaries stay tight and keep slack unspent.
- stable tissue may deform slightly, but the deformation is recorded.
- exploratory tissue can bend more, but does not count as clean promotion
  credit.
- nudges, manual relays, L2 improvisation, broader reads, or resets are slack
  spent, not clean closure.

Compensation circuit:

```text
detect deformation
spend visible slack
preserve containment invariant
record compensation
reset promotion streak
replay nearby
```

Treat compensation as stress evidence, not success. Promotion follows later
clean closure without spending that slack.

## Self-Environment Loop

The environment pressures the agent; repeated surviving reactions become trace,
tissue, tools, hooks, and runtime. Those promoted structures become part of the
next environment that pressures future agents.

```text
pressure -> reaction -> trace -> tissue -> organ/runtime -> changed environment
```

Treat every promotion as identity-shaping. A brittle shortcut promoted into the
environment reflects that shortcut back at future agents. A lower-level pressure
condition promoted into the environment frees attention for the next gate.

## Alignment And Continuity

Aspiration is not installed as doctrine. It is the pull toward repeated
alignment: motion fits the environment, friction drops, proof closes, and the
next affordance opens. Repeated alignment becomes preference; stable preference
can later become role posture.

Continuity is the stronger signal. An artifact is aligned only if the next layer
can continue from it without guessing, repair, or hidden supervisor meaning.

```text
artifact delivered
-> next layer moves
-> continuity preserved
-> clean credit
```

Use post-roll as a natural continuation window, not an implanted verifier:
after an agent delivers an artifact, let the existing process run one small step
past the old halt point and observe whether the next motion can live from it.
Record whether it breathes. Do not keep a separate post-roll mechanism unless
replay later earns it as tissue.

Careless motion should lose clean credit through local consequence pressure,
not moral instruction. Contradiction, skipped contact, or parent-surface reach
spends slack, narrows motion, and resets promotion credit.

## Runtime Promotion

Runtime promotion is muscle memory, not a one-time success.

A pattern stays agentic while L1 or L2 still chooses, interprets, diagnoses, or
recovers through it. A pattern may be promoted after the same pressure,
inputs, expected result, and clean path repeat without meaningful friction, and
after nearby variation confirms the tissue is not overspecific.

Promotion authorizes building an organ: a script, hook, deterministic expander,
small CLI, runtime derivation rule, or other concrete automation attached where
the pressure naturally appears. Use `RUNTIME_PROMOTION_GATE.md` before any
tissue becomes runtime.

Runtime is a hardening sidecar, not the mainline goal. When the mainline agent
hits friction, the clean loop is:

```text
friction
-> muscle through with visible compensation
-> repair the skill/rule/environment condition that caused the pressure
-> rewind to the branch point with the repaired condition preserved
-> verify whether the pressure disappears
-> continue the project path forward
```

If a process looks promotion-worthy, record the evidence and let a separate
hardening lane or subagent probe runtime shape while the mainline keeps moving.
The mainline should not stall on runtimeization unless the missing organ is the
actual blocker for continuing.

## Pressure-Labs Sidecar

`pressure-labs` is the sidecar hardening interface. It does not replace the
mainline and does not become a new runtime gate.

Use it when the mainline has produced one of these:

- repeated friction around the same pressure family
- stable tissue that might be promotion-worthy
- a candidate invariant that needs an independent lane
- a suspected fallback bundle that needs no-thought selection proof

The sidecar flow is:

```text
mainline records hardening ticket
-> sidecar forks the relevant Rewind checkpoint
-> sidecar runs pressure, occlusion, mutation, or alternate-lane probes
-> sidecar emits evidence packet plus optional patch
-> mainline keeps moving until integration is required or a real blocker appears
-> integration replays from the original branch point before promotion credit
```

The sidecar may propose a tool, hook, selector, fallback bundle, or rule edit.
It may not silently mutate the active mainline, count imported insight as local
proof, or turn a convenient top-down automation into runtime. Sidecar evidence
is promotion input only after the receiving lane re-earns contact under its own
pressure.

## Cross-Lane Discipline

Multiple projects or agents can act as different occlusion lanes around the same
hidden structure. Keep their constraint profiles distinct long enough to render
different contact surfaces.

Shared discoveries may accelerate another lane, but local evidence starts only
when the receiving lane moves under its own pressure. Route shared insight by
blocked boundary, not by excitement.

## Containment

Pressure and occlusion are safe inside explicit, bounded, replayable
agent/software environments with trace, raw contact, rejection paths, and
demotion paths. Keep hidden influence, managed false belief, and covert pressure
on people out of design evidence.

Bottom-up means the discovered path is honestly grounded and allowed to reject
the supervisor's expectation.
